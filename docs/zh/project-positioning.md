# 專案定位與能力邊界

[English](../project-positioning.md) | [中文](./project-positioning.md)

---

本文定義 PPT Master 的長期產品定位，以及新增、保留或削減能力時使用的判斷標準。它是一份產品政策，不是功能清單或執行手冊。

本文是[英文規範源](../project-positioning.md)的同步中文譯本，不形成第二套產品政策；定位變化必須在同一次修改中同步兩種語言，如有歧義以英文規範源為準。

當前具體如何選擇路線，仍以 [`workflows/routing.md`](../../skills/ppt-master/workflows/routing.md) 為準。本文回答的是更根本的問題：一個方向究竟是否應該屬於 PPT Master。

## 一、專案定位

> **PPT Master 是一套開源、對話驅動的工作流，讓 AI 先把論證推理成形，再設計併產出真正可編輯的 PowerPoint——不是整頁圖片，也不是一層能改的表皮。它的核心軸線是原生深度：隨著版本迭代，持續創作或保留更多 PowerPoint 自身的物件模型、演示行為和可複用結構。**

輸入可以是一個主題、源材料、資料、設計參考、品牌資產或已有 `.pptx`。主管線負責生成新 deck；其他明確路線和 profile 可以提煉可複用的 Brand / Layout / Deck 工作區，向現有 PowerPoint 填入新內容、重新設計它，或在保留各自契約所承諾內容的前提下追加原生演示行為。

原生深度是一條持續推進的方向，不是一張固定功能清單。PPT Master 的北極星是不斷向 PowerPoint 自身靠攏，縮小 AI 能生成的內容與熟練使用者可以在 PowerPoint 中手工完成的內容之間的差距。[PowerPoint ↔ SVG 能力對映](../powerpoint-svg-mapping.md)逐項、誠實地記錄當前邊界。

從產品形態上看，PPT Master 是一套執行在任意支援 Agent 的 AI 工具中的工作流——也就是一個“skill”。它不是模型，不是託管式演示 SaaS，也不是 PowerPoint 的替代品。工作流負責簡報專用的推理、契約和質量門；確定性工具負責轉換、校驗、打包和可重複的檔案操作；最終質量上限仍由所選模型決定。

最主要的交付物是一份使用者可以直接演示並繼續精修的高質量 PowerPoint 草稿，而不是封閉的最終成品。可複用模板工作區、專案源材料、設計規範、預覽和校驗產物同樣是一等支撐產物，因為它們讓最終 deck 可控制、可重建、可複用。

## 二、產品主張

一份真正有用的 deck 有兩層：讓論證成立的推理層，以及讓結果真正可用的 PowerPoint 構造層。PPT Master 同時負責這兩層。

| 軸線 | 專案立場 | 產品結果 |
|---|---|---|
| 邏輯優先 | 繪製頁面前先確定核心資訊、敘事模式、提綱、層級和證據 | deck 的結構經過推理，而不是機械繼承源材料順序 |
| 原生深度 | 可編輯早已是及格線；真正的問題是可編輯到多深，也就是結果裡究竟有多少 PowerPoint | 在所選路線支援的範圍內，創作或保留真實 PowerPoint 形狀、文字、圖片、圖表、表格、母版與版式、備註、轉場、動畫和 package 行為 |
| 誠實的可編輯性 | 輸出是使用者繼續編輯的草稿，不是扁平圖片，也不承諾一次生成完美終稿 | 視覺保真、資料驅動物件、跨軟體渲染與保留程度之間的取捨必須顯式說明 |
| 使用者控制 | 工作流、專案狀態和輸出都歸使用者所有 | 成本透明；除使用者選擇的 provider 呼叫外，資料留在本地；不強制繫結編輯器、模型或平臺 |

直接 OOXML 過於冗長和脆弱，不適合作為 AI 的通用視覺創作語言；整頁圖片又會丟掉原生物件模型。因此，PPT Master 把適合模型的視覺創作、確定性編譯和直接 package 操作結合起來，並根據使用者意圖選擇正確的修改契約。

因此，專案的工作不只是寫出一個 `.pptx`，而是讓通用 AI Agent 具備可靠完成簡報工作的能力，同時保留使用者檢查、編輯和擁有結果的權利。

## 三、目標使用者與使用方式

PPT Master 主要服務於以下使用者：

- 手上有主題、檔案、資料、視覺參考、品牌資產或已有 deck，需要把它們轉化為簡報。
- 關心 deck 的邏輯和 PowerPoint 可編輯性的深度，而不只是檔案能否以 `.pptx` 開啟。
- 相比幾秒鐘出片，更重視整份 deck 的一致設計和可靠交付。
- 需要本地持有專案、透明控制成本，並保留選擇 AI Agent、模型和 provider 的自由。
- 接受模型決定質量上限，並願意確認關鍵方向，在必要時繼續用 PowerPoint 完成最後一公里。
- 能夠使用對話式 AI 工具和本地 Python 環境，即使本人並不編寫程式碼。

PPT Master 不以零配置瀏覽器出片、即時生成、即時團隊共編，或完全不需要人類判斷和修改的一次性完稿為主要目標。

## 四、產品承諾

| 承諾 | 含義 | 邊界 |
|---|---|---|
| 原生深度 | 在所選路線支援的範圍內，創作或保留真實 PowerPoint 物件、可複用結構和演示行為 | 不把整頁截圖作為規範的 PPTX 生成結果；不支援的語義與有損取捨必須顯式說明 |
| 邏輯先於排版 | 視覺創作前先推理核心資訊、敘事、頁面順序和資訊層級 | 如果某條路線承諾保留原文或結構，就必須遵守該承諾，不能靜默重構 deck |
| 高質量、可繼續編輯的草稿 | 消除從原材料到結構連貫、經過設計且仍可精修的 deck 之間的大部分工作 | 不承諾一次生成完美終稿；模型能力和使用者判斷仍決定上限 |
| 事實與意圖保真 | 區分來源事實、使用者決策、設計建議和派生產物 | 不編造依據，也不把保留型請求靜默改成重新設計 |
| 成本透明且可預測 | PPT Master 保持免費開源；使用者只為自己選擇的 AI 模型和可選 provider 付費 | 不增加專有點數、按席位收費或額外的演示平臺訂閱層 |
| 資料留在本地 | 轉換、創作、校驗和匯出都在使用者機器上完成 | 使用者選擇呼叫的 AI 模型、搜尋、生圖和語音 provider 仍可能接收呼叫所需輸入 |
| 無平臺鎖定 | 任何支援 Agent 的 AI 工具和相容模型都可以驅動工作流，輸出保持可遷移 | 不承諾不同模型產出質量完全一致，也不承諾不同演示軟體渲染完全一致 |
| 工程可靠性 | 使用明確路線、保留契約、質量門、回讀校驗和可恢復專案狀態 | 不用靜默降級掩蓋失敗，也不釋出未通過必需質量門的產物 |
| 質量優先 | 優先保證 deck 一致性、原生可編輯性和交付可靠性 | 可以在不損害質量時提效，但不預設採用低質量並行生成 |

## 五、產品能力模型

PPT Master 的能力範圍比單一生成管線更寬，但有意窄於通用辦公 Agent。

| 能力領域 | 專案責任 |
|---|---|
| 演示推理 | 把主題或材料包轉化為面向受眾的核心資訊、敘事模式、提綱、頁面規劃和明確設計方向 |
| 原生演示創作 | 創作新的頁面視覺，並編譯為真正原生可編輯的 PowerPoint deck |
| 可複用演示設計 | 提煉、建立、組合、校驗並應用 Brand、Layout 和 Deck 工作區 |
| 已有 deck 改編 | 在不同保留契約下重做已有 deck、向原生頁面殼填入新內容，或追加原生演示行為 |
| PowerPoint 表達 | 在溝通目標需要時使用圖片、圖示、圖表、表格、公式、講稿、旁白、轉場和動畫 |
| 審閱與交付 | 預覽、檢查、校驗、修復、匯出、回讀，並保留足夠的本地專案狀態供後續精修或重新匯出 |

這些是產品責任，不代表每項責任都必須暴露成頂層路線或單獨的 workflow 檔案。只有輸入、修改規則、不變數或產物生命週期確實不同，才需要獨立路線。

## 六、專案擁有的責任與接入的能力

PPT Master 可以接入通用能力，但不因此成為這些通用能力的平臺。

| 領域 | PPT Master 負責 | PPT Master 不負責 |
|---|---|---|
| 研究 | 判斷 deck 需要什麼證據、儲存來源，並把研究結果轉化為演示內容 | 與演示任務無關的通用網路研究引擎 |
| 圖片 | 判斷是否需要圖片，並負責圖片的角色、風格、來源、位置、出處和就緒狀態 | 通用圖片生成或圖片管理平臺 |
| 音訊 | 負責演示語境中的講稿、音色選擇、逐頁旁白、計時和 PowerPoint 嵌入 | 通用音訊工作站、播客平臺或語音供應商市場 |
| 資料視覺化 | 選擇表達形式、保留資料、校驗幾何，並顯式呈現可編輯性與保真度之間的取捨 | 通用 BI 或電子表格產品 |
| 模板與品牌 | 定義可複用的演示身份、Master / Layout 結構、槽位、素材與組合契約 | 恢復來原始檔中已經不存在的歷史設計意圖 |
| PowerPoint 編輯 | 負責演示專用的生成、填充、重做和有邊界的原生增強 | 替代 PowerPoint 的完整編輯介面，或支援任意 OOXML 修改 |

倉庫可以內建多個 provider，以保持開放性和實際可用性，但 provider 特有行為應當隔離在穩定的接入邊界之後。演示工作流負責選擇邏輯和輸出語義，任何單一 provider 都不應重新定義產品邊界。

## 七、穩定的技術策略

技術架構服務於定位，但技術架構本身不是專案定位。

- **受約束的 SVG → DrawingML** 是新設計頁面的主要創作和編譯路線：AI 使用適合模型的視覺語言工作，確定性工具再構建原生 PowerPoint 物件。
- **直接 OOXML 操作**用於使用者希望保留現有 PowerPoint package，而不是重新生成視覺設計的場景。
- **模板工作區**在新頁面創作前宣告可複用的品牌身份，以及適用時的 Master / Layout、槽位和素材結構；這些結構不能在事後憑空猜測。
- **sidecar 與 package 級階段**負責演講者備註、旁白、轉場、動畫，以及其他不屬於靜態頁面 SVG 的演示行為。
- **專案產物和質量門**讓過程可檢查、可續跑、可測試，並能安全地重新匯出。

具體實現可以演進，但以下不變數應保持穩定：

1. 不把作為規範交付物的 deck 扁平化成每頁一張圖片。
2. 完整的可見頁面設計必須留在宣告的創作源中；匯出階段不得憑空補造缺失視覺。
3. 明確說明原生可編輯性、視覺保真、資料驅動物件和保留程度之間的取捨。
4. 修改產物前先確定創作或修改契約。
5. 區分源材料、創作產物、派生產物和交付產物。
6. 必需語義無法安全表達時應當停止；不得聲稱不支援的保真度，也不得靜默替換成另一種行為。

## 八、明確不做

PPT Master 不以成為以下產品為目標：

- 零配置、即時出片的瀏覽器演示 SaaS。
- 完全替代人類演示判斷，或承諾一次生成完美終稿的全自動系統。
- 通用辦公助手、研究平臺、圖片平臺、音訊平臺或 provider 市場。
- 完整的 PowerPoint 克隆、完整的瀏覽器自由畫布或即時協作服務。
- 任意 SVG 到 PPTX 或任意 OOXML 的轉換服務。
- 從完成態 PPTX 或 SVG 中恢復缺失的歷史 Master / Layout 意圖。
- 把推斷出的模板結構原地嫁接到已有檔案上的升級器。
- 以犧牲 deck 一致性、原生可編輯性或交付可靠性為代價的速度優先生成器。

這些非目標並不排斥在演示任務中使用研究、圖片、音訊、原生物件或已有 deck。它們防止支撐能力脫離演示語境，發展成承諾完全不同的獨立產品。

## 九、能力准入與削減判據

評估任何新增能力時，按以下順序回答：

1. **使用者任務**：它完成了哪一個真實的簡報任務？
2. **核心貢獻**：它是否提升了 PowerPoint 原生深度、改善了演示推理、增強了使用者控制，或提高了交付可靠性？
3. **責任結果**：它建立或保護了什麼演示產物、決策或質量屬性？
4. **不變數**：什麼必須保持不變，什麼允許改變？
5. **產品層級**：它屬於核心能力、演示專用擴充套件、可替換 provider adapter，還是倉庫維護？
6. **可驗證性**：能否明確檢查成功與失敗，而不是依賴模糊承諾？
7. **真實證據**：是否有真實使用者需求、重複工作流或已經發生的失敗，足以覆蓋維護成本？

| 決策 | 適用條件 |
|---|---|
| 作為核心能力新增或保留 | 直接推進演示任務，或強化原生深度、推理、使用者控制或可靠性，並需要演示專用契約或校驗 |
| 作為整合擴充套件保留 | 能力本身可選，但它的規劃和輸出語義是演示專用的 |
| 放到穩定接入邊界之後 | 底層服務具有通用性或供應商特異性，PPT Master 負責演示專用的選擇邏輯和輸出契約 |
| 移到倉庫工具層 | 服務於倉庫、示例、安裝或貢獻者流程，而不是生產簡報 |
| 退役 | 與另一權威重複、沒有有效使用者、承諾無法驗證，或維護成本高於演示價值 |

檔案或 workflow 的數量本身，不是新增或刪除能力的理由。真正的判斷標準是責任是否清晰，以及它是否創造明確的產品價值。

## 十、北極星結果

一次成功的 PPT Master 使用過程應當是：

> 使用者把主題、源材料、設計參考、可複用模板或已有 PowerPoint 交給 AI Agent。AI 先把論證推理成形，再開始設計；使用者確認真正重要的選擇；工作流最終返回一份結構連貫、經過校驗、具有深度原生能力且可繼續編輯的 PowerPoint，以及足夠的本地專案狀態，用於演示、精修、複用或重新匯出。

未來工作應按以下順序改善這一結果：

1. 原生深度、輸出正確性和交付可靠性。
2. 內容推理、敘事質量和視覺一致性。
3. 品牌、版式、Deck 和已有 PowerPoint 資產的複用。
4. 人工審閱、修正和可控迭代。
5. 能夠強化前四項的額外格式、provider 和便利能力。
